# Design

## Context

See proposal.md — Why. What the toolkit already provides decides most of this:

- `gpui`'s `img` element plays multi-frame images by itself. It advances frames
  on the delay each frame declares, skips animation entirely when
  `cx.reduce_motion()` is set (showing frame 0), stops while the window is
  inactive, and calls `window.request_animation_frame()` for itself while a
  multi-frame image is on screen. Nothing in Knot has to schedule repaints.
- That path is **GIF and WebP only**. `img` dispatches on the decoded format and
  only those two go through a frame decoder; a PNG — including an APNG — is
  decoded as a single frame and will not animate.
- `with_transformation` (rotate/scale/translate) exists on `svg`, not on `img`,
  and the icon exists only as PNG and ICNS. Rotating the still icon at runtime
  is therefore not available without first authoring an SVG, which is as much
  new art as the animation itself.
- The panel's Working row already exists (`PanelRow::Working`, counted by
  `row_count` from `turn_active`) and is the only caller that pins
  `working_indicator::render` to `(Running, true)`. The dashboard card is the
  other caller and uses all five states.
- `spinner_repaint_due` and `WORKING_INDICATOR_MIN_REPAINT` exist for the
  dashboard, which redraws only on events. The panel redraws as it streams.

## Goals / Non-Goals

**Goals:**

- Let the toolkit own the animation. No frame counter, no clock read on the
  render path, no addition to the repaint poll.
- Keep the asset reproducible from something already in the repository, so it
  can be regenerated rather than treated as opaque committed bytes.

**Non-Goals:**

- Changing the dashboard's indicator or the poll that drives it.
- An animation abstraction. One element plays one asset.

## Decisions

### An animated WebP asset, played by `img`

The indicator is `img(<animated webp>)` in a fixed-size box. GPUI's own
animated-image handling then supplies frame timing, the reduced-motion
behavior the spec requires, the inactive-window pause, and the repaint
scheduling.

The alternative — a still image plus a frame index the app advances, in the
shape of today's `spinner_frame()` — was rejected. It would need its own
repaint driver in the panel, its own reduced-motion check, and its own
"is the window active" check, all of which the toolkit does already, and it
would put a clock read back on the render path.

WebP over GIF because the icon has a soft alpha edge and GIF transparency is one
bit, which fringes against both themes. WebP costs bytes for that rather than
saving them, which the pre-implementation estimate had backwards: measured on
the real icon at the settings actually shipped (24 frames at 72×72), the GIF is
68KB with a hard alpha cutoff and the WebP is 95KB with full alpha. Edge quality
is the whole reason for the choice, so the choice stands — but it is a trade,
not a free win. GIF stays the fallback if `img2webp` proves unavailable; it
works and it is playable, it just looks worse at the edge.

**This needs a tool the machine does not have.** `ffmpeg` is installed but its
build has no `libwebp` encoder, so assembling the animation needs
`brew install webp` for `img2webp`. Frame generation, which is the part that
touches the artwork, works with the `ffmpeg` already present — verified against
`assets/icon/icon.png`.

### The animation is a plane rotation of the committed icon, generated by script

Frames come from `crates/knot/assets/icon/icon.png` (512×512 RGBA) rotated
through one full turn with `ffmpeg`'s `rotate` filter with `c=none` to preserve
alpha, then assembled into a looping WebP. The whole pipeline goes in
`scripts/make-working-animation.sh` beside the existing
`scripts/check-file-size.sh`, so the asset is regenerable rather than a binary
nobody can reproduce. It is not wired into `make` — it needs tools CI does not
have, and the asset changes roughly never.

Verified: 24 frames at 72×72 come out intact, alpha preserved with no fringe
against a dark surface, with the knot clearing the canvas corners at every angle
(it is a round form in a square frame, so rotation cannot clip it). One
revolution is 24 × 62ms = 1488ms, and frame 24 would be frame 0 again, so the
loop closes with no seam.

Alternatives considered:

- *A 3D turntable render.* The honest cost of a plane rotation is that the
  lighting rotates with the object rather than the object turning under fixed
  light. A turntable would fix that and needs the icon's 3D source, which is not
  in this repository. If that source ever lands, it replaces the asset bytes and
  no code changes — the loading site takes bytes, not a rotation.
- *A pulse or breathe.* Avoids the lighting problem, but at the size of this row
  a scale-and-fade reads as throbbing rather than as work in progress.

### Size: a 24px slot, authored at 72×72

The row today is a 12×16 box holding one character, which is the size the
proposal calls a stray glyph. 24px is legible as a deliberate mark and still
subordinate to the conversation.

The asset is authored at 72×72 — 3× the slot, which still clears the 48 device
pixels a 2× display asks for. Not the 4× `assets/app-icon-32.png` uses for its
16px slot: a rotation gives every frame different alpha, so nothing compresses
across frames and the file scales with area × frame count, which a still icon's
ratio says nothing about. 4× at 30 frames measured 182KB against the ~100KB
ceiling under Risks; 3× at 24 frames is 95KB. Encoder quality is not the lever —
q80 to q60 saved 12% — so area and frame count are what came down.

The box is fixed in both dimensions so the row reserves the same space whether
the animation plays or is held still, which is what the spec's no-reflow
scenario asks for.

### The panel stops calling `working_indicator`

`PanelRow::Working` renders the new element directly. `working_indicator.rs` is
untouched in behavior; its module doc records that the panel no longer calls it
and points at the `working-indicator` spec delta for why.

The loading site is a sibling of `app_titlebar_icon` in `app_support.rs`, so
both icon assets are built the same way in the same place.

## Risks / Trade-offs

- **Reduced motion leaves a still icon that does not obviously mean "working"**
  → The spec makes presence, not motion, the carrier: the row exists only while
  a turn is active. This is weaker than the animation and is the accepted cost
  of honoring the setting; adding a text label instead would be a different
  change.
- **The animation pauses when the row is scrolled out of the virtualized list,
  or the window is inactive** → Both are invisible by definition — nobody is
  looking at it — and both save repaints. No mitigation needed, but do not
  "fix" either by forcing repaints.
- **A binary asset in git that only one script can regenerate** → The script is
  committed with it, and it derives from an icon already in the tree, so the
  input is versioned too. Keep the asset small; if it exceeds roughly 100KB,
  drop the frame count or the dimensions rather than accepting the weight. Not
  hypothetical: the first generated asset was 182KB, and the frame count and
  dimensions came down to meet this, as recorded under Size above.
- **`img2webp` is an extra tool for whoever regenerates the asset** → It is
  needed only to regenerate, never to build or run Knot, and the script should
  say so and fail with that message rather than a missing-binary error.
- **The icon at 24px is a busy image** → It is a detailed 3D render and will
  read as a colored blob at this size. That is acceptable for a motion cue,
  where movement rather than detail carries the meaning, and is why the
  dashboard card — where the mark must be *distinguished* from three others —
  is deliberately not adopting it.
