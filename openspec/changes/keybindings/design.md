# Design

## Context

- Every binding is installed once, in `app_bootstrap::install_actions_and_keys`.
  Each is a context-less `KeyBinding::new(chord, action, None)`.
- `gpui_kit::init` binds its components' keys into the same keymap. That is
  why `cx.clear_key_bindings()` cannot be used to rebind: it would erase the
  text inputs' own keys.
- The menu bar is a static snapshot. `set_app_menus` reads each item's key
  equivalent from the keymap at build time.
- Workspace-scoped behavior is handled per window on the root element, like
  the Agents menu actions (`agent_menu.rs`). A global handler would make the
  action available with no workspace window focused.
- The workspace view mode is `WorkspaceViewMode::{Terminal, Dashboard,
  PullRequests}`, with `toggled()`, which the sidebar rows already use. Agent
  selection goes through `WorkspaceWindow::reveal_agent`. Pane focus is latched
  by `focused_pane` in `focus_showing_pane`.

## Goals / Non-Goals

**Goals:**

- One module owns the configurable shortcuts: their defaults, how a stored
  value turns into bindings, validation, and runtime rebinding.
- Rebinding does not disturb any binding it does not own.

**Non-Goals:**

- A general user keymap file, or a Zed-style JSON keymap.
- Context-scoped (`KeyContext`) bindings. The app has none today, and adding
  them changes precedence for every existing binding.

## Decisions

### Rebind with `Unbind` markers, not `clear_key_bindings`

To move a shortcut, `keymap::apply` binds `gpui::Unbind(action_name)` on the
old chord and then binds the action on the new chord. `Keymap::bindings_for_*`
drops a binding when a later `Unbind` names both its keystroke and its action,
so this removes exactly the pair being replaced. Other bindings on the same
chord are untouched.

The module keeps the currently applied chords in a global, which is what tells
it the "old" chord to unbind. The keymap grows by two entries per change. That
is negligible for a user-driven setting.

- Alternative: `clear_key_bindings`, then re-run every bind site. Rejected
  because `gpui_kit::init`'s bindings are not ours to replay.
- Alternative: bind `NoAction` on the old chord. Rejected because that disables
  the chord for every action, including a gpui component that also uses it.

After `apply`, the caller rebuilds the menus from the current
`AgentMenuSnapshot`, so the Command Center item shows the new key.

### Numbered families are nine unit-struct actions, not a payload action

`SelectWorkspace1`…`SelectWorkspace9` and `SelectAgent1`…`SelectAgent9` are
generated by `actions!` and mapped to an index by a single table. `Unbind`
matches on the action *name*. A payload action (`SelectWorkspace { index }`)
gives all nine the same name, so unbinding one binding would unbind all nine.
With unit actions each binding can be moved on its own, and a menu item could
show a specific digit if menus are ever added.

### Handler placement

- Select workspace N and Open Command Center are global (`cx.on_action`). They
  must work with no Knot window focused. The workspace handler resolves N
  against `store.workspaces()` order and calls `WorkspaceWindow::open`, which
  already raises an open window instead of opening a second one.
- Select agent N, Focus agent input and the two panel toggles are registered on
  the workspace window's root element. Unbound elsewhere, they do nothing in
  the Command Center, the manager or the settings window.
- Select agent N indexes the same ordered list the sidebar renders, and calls
  `reveal_agent`.
- Focus agent input sets the view mode to `Terminal`, then focuses the composer
  or the terminal directly and records it in `focused_pane`. Going through
  `focus_showing_pane` would hit its "already focused" early return when focus
  has moved inside the same pane, such as to the git panel's commit field.

### Storage

A `KeybindingSettings` struct is added to `knot_core::Settings`
(`#[serde(default)]`):

- `workspace_select_modifiers` and `agent_select_modifiers`: `ShortcutModifiers
  { command, control, alt, shift }`, each `Option`. `None` means the default.
- `focus_input`, `toggle_dashboard`, `toggle_pull_requests` and
  `open_command_center`: `Option<String>`, holding a gpui keystroke string such
  as `"cmd-alt-p"`. `None` means the default.

Only a customization is stored, so a future change to a default reaches users
who never customized that shortcut. The fields are named rather than a map
keyed by an enum: an unknown key in a map fails the whole document decode,
while an unknown field is ignored. That keeps the store decode-tolerant
(`settings-persistence`).

Parsing and validation live in the `knot` crate (`keymap::resolve`), because
`Keystroke::parse` is gpui's. `knot-core` stays free of gpui. At launch,
`resolve` substitutes the default for any stored value that does not parse, or
that fails validation.

### Validation is one pure function

`keymap::validate(&proposed, &fixed) -> Result<Resolved, Rejection>` checks:

- modifier presence (⌘, ⌃ or ⌥);
- collisions within the configurable set, with the nine digits expanded;
- collisions with the fixed chords, which come from a list the bootstrap
  bindings are also built from.

It is a pure function because it has to be unit-tested without a window. The
fixed list moves beside the configurable one, into `keymap`, so a new fixed
shortcut cannot be added without the validator seeing it. `Rejection` carries
an l10n key and the conflicting shortcut's label.

### Recorder

The Keyboard pane arms a recorder by focusing a dedicated `FocusHandle` whose
element takes `on_key_down`. The first keystroke with a non-modifier key ends
recording. Escape cancels. Anything else goes through `validate`.

While a recorder is armed, a pressed chord that is already bound would still
dispatch its action. To prevent that, the recorder element calls
`cx.stop_propagation()` / `window.prevent_default()` in a capture-phase key
handler, so the chord is consumed before it reaches the keymap.

## Risks / Trade-offs

- [Risk] AppKit claims a menu key equivalent before the window. With no menu
  items for the new shortcuts, only the Command Center's rebinding touches a
  menu. → Rebuild the menus after every `apply`, and cover it in a test that
  reads `bindings_for_action(OpenCommandCenter)`.
- [Risk] The terminal pane forwards keystrokes to the PTY, so it could see
  ⌥⌘digit or ⌘L before the keymap does. → Existing context-less ⌘-chords (⌘D,
  ⌘R) already dispatch ahead of the terminal. A test dispatches the new chords
  with the terminal focused.
- [Risk] ⌥⌘digit may be taken by a user's system-wide tool. → That is what the
  customization is for.
- [Trade-off] A shortcut cannot be left unbound. This keeps the storage and the
  UI simpler, and is listed as a non-goal.

## Migration Plan

No migration. Missing fields decode to `None`, which means defaults. Rolling
back to an older build ignores the unknown `keybindings` field.
